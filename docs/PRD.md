## 【 PRD 】 HWP 리더 — 안드로이드 경량 문서 뷰어

| 항목 | 내용 |
| --- | --- |
| 버전 | v0.2 (초안) |
| 작성일 | 2026-10-15 |
| 수정일 | 2026-10-16 — M0 빌드 실측 수치 반영(0·6·8장), 시스템 글꼴 크기 반영 방식 기록(6장) |
| 상태 | 검토 중 — 15장 '결정 필요 사항' 확정 후 v1.0 |
| 엔진 | kordoc v4.21.33 (MIT, github.com/chrisryugj/kordoc) + Android PdfRenderer |

표기: **[Fact]** 코드·공식 문서·실측으로 확인 / **[Assumption]** 추정·목표치, 검증 필요

---

### 0. 요약

- **목적**: 휴대폰에서 HWP·HWPX·PDF·PPTX·MD 문서를 앱 하나로, 오프라인으로, 빠르게 연다. 편집 기능은 없다.
- **구조**: Kotlin 앱 안의 WebView에서 kordoc 브라우저 번들을 실행한다. PDF는 안드로이드 내장 PdfRenderer로 연다.
- **검증**: 2026-10-15 스파이크에서 kordoc 소스를 고치지 않고 브라우저 번들을 만들었다. HWP 2건, HWPX 2건, PPTX 1건이 모두 열렸다. kordoc 번들은 1.3MB(gzip 447KB)다. [Fact]
- **M0 빌드 실측(2026-10-16)**: R8을 켠 릴리스 APK는 2.0MB로 목표(10MB)의 5분의 1이다. 뷰어 번들은 엔진 1.5MB + 화면 183KB다. [Fact — 6장]
- **보안 원칙**: 인터넷 권한을 선언하지 않는다. 그래서 문서가 기기 밖으로 나갈 통로가 처음부터 없다.
- **결정 필요**: ① 구형 .ppt 지원 여부 ② 배포 범위(개인용·기관 공식) ③ 원내 문서 DRM 적용 비중. 상세는 15장.

---

### 1. 배경과 문제

○ 현황
- 원내외 업무 문서는 대부분 HWP·HWPX다. 휴대폰에서 열려면 무거운 오피스 앱을 써야 하고, 이런 앱은 광고·로그인·클라우드 업로드를 함께 요구하는 경우가 많다.
- 한컴오피스 Viewer 같은 기존 앱이 있다. 다만 일부 지역 App Store 페이지에는 판매·지원 종료 문구가 붙어 있어, 안드로이드판 지원 상태는 확인이 필요하다.
- 대상 문서는 일반 업무 문서다(대외비 아님). 그래도 외부 서버를 거치지 않고 기기 안에서 바로 여는 편이 빠르고 단순하다.

○ 대상 사용자
- 원내 기획·행정 실무자. 메신저·메일로 받은 첨부 문서를 이동 중에 확인한다.
- 기대 수준: "열리기만 하면 된다. 잘 보이면 된다."

○ 해결 방향
- 문서를 기기 안에서만 처리하는 단일 목적 뷰어. 기능을 더 넣기보다 빼는 쪽으로 설계한다.

### 2. 목표와 비목표

○ 목표
- **G1 열기**: 지원 형식 파일을 '다른 앱으로 열기' 한 번에 연다.
- **G2 가벼움**: APK 10MB 이하, 콜드 스타트 1초 이하, 20쪽 문서 첫 쪽 표시 2초 이하(중급 기기 기준). [Assumption — 목표치, M0에서 실측 후 확정]
- **G3 깔끔함**: 장식을 빼고 문서가 화면을 차지하게 한다.
- **G4 안전**: 네트워크 권한이 없고, 남기는 기록을 최소화한다.

○ 비목표 (v1에서 하지 않음)
- 편집, 저장, 형식 변환(PDF 내보내기), 인쇄
- 클라우드 연동, 계정, 동기화, 광고
- OCR, AI 요약, 번역
- 구형 바이너리 오피스 형식(.ppt, .doc, .xls). 15장 D1 결정에 따른다.
- DRM 해제. 기술적으로 불가능하고 보안 정책에도 반한다.

### 4. 지원 형식과 보기 방식

보기 방식은 두 가지다.
- **원본 보기**: 쪽 모양을 그대로 그린다. kordoc의 레이아웃 보존 SVG 렌더러를 쓴다.
- **읽기 모드**: 화면 폭에 맞춰 글을 다시 흘린다. kordoc이 Markdown으로 변환하고 markdown-it이 HTML로 그린다.

| 형식 | 처리 엔진 | 원본 보기 | 읽기 모드 | 비고 |
| --- | --- | --- | --- | --- |
| HWP 5.x | kordoc `renderDocumentToScene`, `parseHwp` | ○ | ○ | 배포용 문서 복호화는 Node `crypto` 없이 순수 TS AES로 구현돼 있다 [Fact: `src/hwp5/crypto.ts`]. 브라우저 동작은 실파일로 확인 필요 [Assumption]. 암호 문서는 P2 |
| HWPX | kordoc `renderDocumentToScene`, `parseHwpx` | ○ | ○ | 조판 캐시가 없으면 kordoc 자체 조판(reflow)으로 그린다 [Fact: `src/render/document.ts`] |
| HWP 3.x | kordoc `parseHwp3` | × | ○ | kordoc 렌더러는 HWPX·HWP5만 지원 [Fact] |
| PDF | Android `PdfRenderer` | ○ | × | 텍스트 검색·선택은 v1 제외 |
| PPTX | kordoc `parsePptx` | × | ○ | 슬라이드 모양 렌더 기능은 kordoc에 없다. 제목·목록·표·그림·발표자 노트만 추출 [Fact: `src/pptx/parser.ts`] |
| PPT (97–2003) | — | × | × | kordoc 미지원 [Fact: `detectZipFormat`은 ZIP 기반 PPTX만 판별]. 안내 메시지만 표시 |
| MD | markdown-it | — | ○ | kordoc 의존성 중 하나. 번들 +144KB(gzip 51KB) [Fact] |

- 원본 보기 실패 시 읽기 모드로 자동 전환하고 상단에 한 줄로 알린다.
- DOCX·XLSX도 kordoc이 지원하므로 추가 비용이 작다. P2 후보로 둔다.

### 5. 기능 요구사항

○ P0 — v1 필수

| ID | 기능 | 요구사항 |
| --- | --- | --- |
| F1 | 파일 열기 | `ACTION_VIEW`·`ACTION_SEND` 인텐트 수신, 앱 안 '파일 열기'(SAF `ACTION_OPEN_DOCUMENT`). 저장소 권한은 요청하지 않는다 |
| F2 | 형식 판별 | 확장자·MIME을 믿지 않고 파일 앞부분 바이트(매직바이트)로 판별한다. kordoc `detectFormat`·`detectZipFormat`과 `%PDF` 헤더를 쓴다. kordoc `detectFormat`은 OLE 파일을 모두 `hwp`로 돌려주므로 [Fact: `src/detect.ts`], 셸이 OLE 안 스트림 이름으로 HWP5와 구형 오피스(.ppt·.doc)를 한 번 더 가른다 |
| F3 | 원본 보기 | 세로 연속 스크롤, 핀치 줌(최대 400%), 더블탭으로 폭 맞춤, 쪽 표시 "3 / 24" |
| F4 | 읽기 모드 | 화면 폭 맞춤 줄바꿈, 글자 크기 3단계, 넓은 표는 가로 스크롤 |

| F6 | 최근 문서 | 최대 20개, 영구 URI 권한(`takePersistableUriPermission`) 사용. 기록 끄기와 전체 삭제 제공 |
| F7 | 오류 안내 | 암호·DRM·미지원·손상·용량 초과를 구분해 안내한다(10장) |
| F8 | 고지 화면 | 오픈소스 라이선스와 한컴 공개 문서 고지(11장) |

| --- | --- | --- |
| F9 | 문서 내 검색 | 읽기 모드 우선. 원본 보기 강조는 kordoc `highlights` 옵션 활용 검토 |

○ P2 — 후속 버전

- 암호 HWP·HWPX: 현재 `crypto` 대체 모듈(shim)을 WebCrypto나 순수 JS 암호 라이브러리로 교체해야 한다.

- DOCX·XLSX 읽기 모드
- 화면 캡처 차단 옵션(`FLAG_SECURE`)

| ID | 요구사항 | 이유 |

| SEC-7 | R8 난독화 적용 | 「모바일 전자정부 서비스 관리 지침」 별표1 제20호, 별표3 제26호의 난독화 항목 |

○ 적용 기준 확인
- 「모바일 전자정부 서비스 관리 지침」(행정안전부 예규, 최종 2026-05-12)은 공공기관의 모바일 서비스에 적용된다(제1조). 기관 내부 업무용 앱은 '모바일 행정서비스'(제2조제4호)에 해당할 수 있다. [Fact: 법제처]
- 기관이 업무용으로 공식 배포하면 제26조(개발보안: 보안약점 진단·제거, 하이브리드 앱은 웹·앱 기준 모두 적용)와 제27조(정기 보안취약점 점검)를 적용받을 수 있다.
- 개인용 도구로 쓸 때도 이 기준이 적용되는지는 정보보안 부서 확인이 필요하다. 이 PRD는 어느 쪽이든 통과하도록 설계했다(SEC-1~7).

### 8. 기술 구조

○ 전체 흐름

```
[카카오톡·메일·파일 앱] ──Intent(URI)──▶ [Kotlin 셸]
                                          │ 형식 판별(매직바이트)
                ┌─────────────────────────┴──────────────────────────┐
                ▼ PDF                                                  ▼ HWP·HWPX·PPTX·MD
      [PdfRenderer → 쪽 비트맵 뷰]              [WebView: assets/viewer.html + kordoc-viewer.js]
                                                  ├ 원본 보기: renderDocumentToScene → 쪽 SVG
                                                  └ 읽기 모드: parse → Markdown → markdown-it → HTML
```

○ 8.1 셸(네이티브)
- Kotlin, 단일 Activity. 화면은 홈(최근 문서), 뷰어, 설정·고지 3개다.
- UI 도구는 Jetpack Compose(Material 3)를 권장한다. View 시스템보다 APK가 약 2MB 커지는 대신 개발 속도가 빠르다. [Assumption — View 시스템판은 만들지 않아 차이는 재지 않았다]
- Compose를 쓴 릴리스 APK 전체가 2.0MB이고, 그중 dex(Compose 포함 Kotlin 코드)는 1,119KB다 [Fact: 2026-10-16 빌드]. 목표 G2에는 문제가 되지 않는다.

○ 8.2 kordoc 통합 방식 비교

| 방식 | 내용 | 용량 | 유지보수 | 판단 |
| --- | --- | --- | --- | --- |
| **A. WebView + JS 번들** | kordoc 소스를 브라우저용으로 묶어 앱 assets에 넣는다 | +1,790KB(APK 안 압축 611KB) | kordoc 버전 갱신 시 재번들만 하면 된다 | **추천** — 스파이크로 동작 확인 |
| B. JS 엔진 내장(QuickJS 등) | WebView 없이 JS만 실행 | +1~3MB | 결과물이 SVG·HTML이라 표시하려면 결국 WebView가 필요하다 | 이점 없음 |
| C. Kotlin으로 포팅 | 파서를 직접 옮긴다 | 최소 | kordoc 개선을 따라갈 수 없다. 수개월 소요 | 비추천 |
| D. Node 런타임 내장 | nodejs-mobile 등 | +수십MB | 목표 G2와 충돌 | 비추천 |

○ 8.3 kordoc 브라우저 번들 구성 (스파이크로 확인)

kordoc은 Node.js 20 이상을 전제로 만들어졌다. Node 내장 모듈을 쓰는 곳은 아래처럼 대체했고, **kordoc 소스는 한 줄도 고치지 않았다.** [Fact]

| Node 모듈 | 쓰는 곳 | 대체 |
| --- | --- | --- |
| `zlib` | HWP5 레코드·HWPX ZIP 압축 해제 | `pako` |
| `stream` | JSZip 스트림 읽기(`readZipEntry`) | `readable-stream` + `events` |

○ 8.4 문서 전달 방식 (네이티브 → WebView)
- 뷰어 페이지(`viewer.html`·번들)는 `WebViewAssetLoader`로 앱 assets에서 읽는다. 외부 주소는 열지 않는다.
- 문서 바이트 전달 1안: `androidx.webkit`의 WebMessagePort로 ArrayBuffer를 그대로 넘긴다. 복사가 적고 빠르다.
- 문서 바이트 전달 2안: 1안을 지원하지 않는 기기에서는 Base64로 나눠 넘긴다. 크기가 33% 늘고 메모리를 약 2배 쓴다.
- INTERNET 권한 없이 위 방식이 모두 동작하는지는 실기기에서 확인해야 한다. [Assumption — M0 확인 항목]

○ 8.5 대용량 처리
- 24쪽 HWPX의 SVG 합계가 3.2MB였다 [Fact]. 100쪽이면 13MB 안팎으로 추정된다. [Assumption]
- 모든 쪽을 한 번에 DOM에 붙이지 않는다. 화면 근처 쪽만 붙이는 가상 스크롤을 쓴다.
- 렌더링은 Web Worker에서 돌려 화면 멈춤을 막는다. kordoc은 XML 해석에 브라우저 DOM이 아닌 `@xmldom/xmldom`을 써서 Worker에서도 돌 것으로 본다. [Assumption — M0 확인]
- 읽기 모드 그림은 kordoc이 Markdown과 별도로 돌려준다(예: `image_001.jpg`). 뷰어가 이를 `blob:` URL로 연결해야 한다. [Fact: 스파이크]
- WMF·EMF 그림은 브라우저가 표시하지 못한다. kordoc 변환 지원 범위를 확인해야 한다. [Assumption]

○ 8.6 글꼴
- kordoc SVG는 CSS 글꼴 목록을 지정한다(예: `'HCR Batang','Batang','Noto Serif KR',serif`) [Fact: `src/render/head-styles.ts`]. 안드로이드에는 함초롬·맑은고딕이 없어 시스템 Noto CJK로 대체된다.
- kordoc은 줄 위치를 원본 글꼴 폭 기준으로 계산한다. 그래서 대체 글꼴의 폭이 다르면 글자가 겹칠 수 있다. 스파이크에서도 머리글 일부 겹침과 옛한글 자모 분리가 보였다. 컨테이너 글꼴 기준이므로 실기기에서 다시 확인해야 한다.

| 선택지 | 용량 | 판단 |
| --- | --- | --- |
| a. 시스템 글꼴만 사용 | 0MB | **v1 기본값** |
| b. 오픈 글꼴(Noto Serif/Sans KR, OFL) 일부만 번들 | +수MB | M0에서 겹침이 많으면 채택 |
| c. 함초롬체 번들 | +수MB | 재배포 라이선스 확인 필요 |

○ 8.7 kordoc 버전 관리
- 변경 속도가 매우 빠르다. 4.21.31(10-13)부터 4.21.33(10-15)까지 사흘간 3개 버전이 나왔고, 최근 이틀 커밋은 50건이다. [Fact]
- 특정 버전을 고정한다. 분기 1회 갱신하고, 갱신 때마다 회귀 문서 세트(개인정보를 제거한 원내 양식 20~30종)로 확인한다.
- `@xmldom/xmldom` 0.9.10은 npm에서 deprecation 경고("critical issues")가 붙어 있고, 0.9.12가 나와 있다 [Fact: npm]. 번들할 때 최신 패치판으로 고정한다.

### Critical Review

- **이 안을 채택하면 안 되는 가장 강한 이유**: kordoc은 Node 전용으로 설계·검증됐다. 브라우저 실행은 공식 지원 범위 밖이다. 변경 속도가 빠른 상류를 대체 모듈로 따라가는 부담이 1인 개발자에게 계속 쌓인다(R1).
- **한계·위험**: 성능 목표(G2)는 실기기 데이터 없이 정한 값이다. 글꼴 대체로 생기는 레이아웃 어긋남은 kordoc 구조상 완전히 없앨 수 없다.
- **추가 검증 필요**: D4(DRM 비중), 실기기 WebView 성능, INTERNET 권한 없는 문서 전달, 원내 표본 렌더 품질.
- **사전 부검(1줄)**: 6개월 뒤 실패했다면, 원내 문서 대부분이 DRM이라 열리는 문서가 적었거나, kordoc 갱신 때 번들이 깨져 오래된 버전에 묶였기 때문일 가능성이 높다.
- **Plan B**: R1·R5 대응을 따른다. 버전 고정과 포크로 상류 의존을 끊고, DRM 비중이 높으면 앱 범위를 외부 수신 문서용으로 좁힌다.
